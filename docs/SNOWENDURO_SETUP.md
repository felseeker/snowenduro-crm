# SnowEnduro CRM: подготовка

## Проверка интерфейса без базы

Для проверки кода и просмотра экрана нужны Node.js 24 и npm, Docker не нужен.

1. Установить зависимости: `npm ci`.
2. Проверить типы и production-сборку: `npm run typecheck` и `npm run build`.
3. Запустить тесты Edge Functions: `npm run test:unit:functions`.
4. Запустить интерфейс: `npm run start`.

Без отдельного адреса Supabase CRM показывает страницу подключения и не включает демонстрационную базу. Эти команды не обращаются к другой CRM или базе пользователя. Проверку входа, сохранения заявок, каталога и фотографий можно выполнить только после настройки отдельного сервера и безопасных ключей.

В браузерной части нужны только `VITE_SUPABASE_URL` и `VITE_SB_PUBLISHABLE_KEY`. Для административных скриптов задаются временно в окружении `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `ADMIN_EMAIL` и `ADMIN_PASSWORD`. Не записывайте service key, пароль администратора, токен Telegram или GitHub в Git, `VITE_*` переменные, страницы сайта или журналы команд.

Скопируйте `.env.example` в личный файл окружения, который исключён из Git, и замените все примеры. Не используйте серверный ключ production для локальной разработки.

## Первая учётная запись и перенос каталога

- `npm run admin:create` создаёт первую подтверждённую учётную запись только в пустой базе. Повторный запуск не сбрасывает пароль существующей учётной записи и не повышает права другого пользователя.
- `npm run catalog:seed` добавляет отсутствующие товары из `supabase/seed/catalog.json`. Конфликтующие существующие записи и товары не перезаписываются и не удаляются.
- В seed сохранены 19 товаров из текущего каталога SnowEnduro. Фотографии, уже лежащие в папках сайта, продолжают использоваться как статические URL. Новые фотографии CRM сохраняет в закрытом Supabase Storage.

## Публикация каталога на GitHub Pages

Публикация выполняется отдельным workflow в репозитории сайта. CRM передаёт GitHub только идентификатор задания; данные каталога запрашиваются workflow у защищённой серверной функции по HMAC-подписи. В репозитории сайта задаются переменная `SNOWENDURO_CATALOG_API_URL` с корневым адресом API и секрет `SITE_CATALOG_SYNC_SECRET`; на сервере CRM хранится тот же HMAC-секрет. Токен `SITE_GITHUB_TOKEN` хранится только на стороне CRM и ограничивается правом запуска workflow нужного репозитория.

Workflow получает опубликованный каталог, скачивает изображения из закрытого хранилища по коротким подписанным ссылкам, записывает JSON и файлы в репозиторий сайта и выкладывает статическую сборку в GitHub Pages. Заявки и клиентские данные в этот workflow не передаются. Обычная публикация сайта использует ту же сохранённую версию каталога.

Настройки сборки сайта `NEXT_PUBLIC_SNOWENDURO_CRM_API_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `NEXT_PUBLIC_SNOWENDURO_PRIVACY_POLICY_VERSION` и `NEXT_PUBLIC_SNOWENDURO_LEAD_FORM_ENABLED` задаются как публичные переменные GitHub Actions. Публичный ключ допустим в статическом сайте; service role key — нет. Флаг формы оставляется `false`, пока владелец не утвердит тексты политики и согласия и не настроит российскую базу. После этого надо отдельно включить этот build-флаг и `PUBLIC_LEAD_INTAKE_ENABLED` на сервере.

Если GitHub Actions недоступен, уже опубликованная статическая версия сайта продолжает работать. Статус и ошибка синхронизации сохраняются в CRM; повторный запуск создаёт новое задание.

## Серверные секреты

Задать только в серверном окружении Edge Functions:

- `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` — доступ к базе от имени сервера.
- `PUBLIC_LEAD_INTAKE_ENABLED=false` — закрытый режим по умолчанию.
- `PRIVACY_POLICY_VERSION` и `LEAD_RATE_LIMIT_HMAC_SECRET` — включение формы после утверждения политики и настройки ограничений.
- `PUBLIC_SITE_ORIGINS`, `CRM_ORIGINS`, `CRM_PUBLIC_URL` — адреса сайта и CRM.
- `TELEGRAM_BOT_TOKEN` — токен бота; Chat ID получателей находятся в закрытой базе.
- `SITE_GITHUB_TOKEN`, `SITE_GITHUB_OWNER`, `SITE_GITHUB_REPO`, `SITE_GITHUB_WORKFLOW`, `SITE_GITHUB_BRANCH` — запуск публикации каталога.
- `SITE_CATALOG_SYNC_SECRET` — общий случайный секрет подписи для сервера и GitHub Actions. Не передавать его через входные параметры workflow.

Ключи следует передавать через защищённый механизм секретов выбранной российской инфраструктуры. Для статической CRM на GitHub Pages `CRM_ORIGINS` должен включать origin `https://felseeker.github.io`; `CRM_PUBLIC_URL` по умолчанию ведёт на `https://felseeker.github.io/snowenduro-crm`. Файл `.env.example` содержит пустые значения и не является готовым production-конфигом.

## Подключение получателей Telegram

Создайте бота через [@BotFather](https://t.me/BotFather) и сохраните выданный токен только в серверных секретах. Каждый личный получатель должен открыть бота и нажать `/start`; для группы добавьте туда бота и отправьте `/start` в группе. В разделе Telegram нажмите «Найти чаты с /start», выберите нужные числовые Chat ID и сохраните список. CRM читает только идентификаторы и тип чата, не сохраняет текст команд и не добавляет найденные чаты без решения администратора. Поиск использует Telegram `getUpdates`, поэтому для этого бота нельзя заранее настраивать webhook.

## Персональные данные и включение форм

Ввод имён и телефонов сейчас должен оставаться отключённым. Перед включением владелец должен определить оператора обработки, цели и сроки хранения, адрес для обращений, фактических обработчиков и российское место хранения; после этого требуется обновить `/privacy`, тексты согласия и политику удаления данных. По действующей редакции статьи 18 закона № 152-ФЗ первичная запись, систематизация, накопление, хранение, уточнение и извлечение данных российских граждан должны выполняться в базах на территории России, кроме прямо установленных исключений. Статья 22 требует уведомить Роскомнадзор до начала обработки, если конкретный оператор и цель не подпадают под исключение. Эти положения нужно проверить применительно к владельцу и правовому основанию проекта до открытия формы.

В конфигурации формы есть два независимых закрытых условия: `PUBLIC_LEAD_INTAKE_ENABLED=true` на сервере и версия политики, совпадающая с версией в форме. Одной публикации сайта недостаточно для включения приёма заявок.

## Рекомендуемое размещение

GitHub Pages остаётся публичным хостингом сайта. CRM можно собрать как статические файлы и разместить отдельно; Supabase/PostgreSQL, файлы заявок, API и резервные копии размещаются в российском регионе.

Supabase self-hosted вариант можно развернуть на отдельном российском сервере. Для него документация Supabase описывает Compose-конфигурацию и указывает минимум 2 vCPU, 4 ГБ RAM и 40 ГБ SSD для полного набора сервисов, рекомендуя 4 vCPU, 8 ГБ RAM и 80 ГБ SSD. Ориентир Yandex Cloud для постоянно включённой VM 2×100% vCPU / 4 ГБ с 40 ГБ быстрым SSD — около 3 310 ₽ в месяц за CPU, RAM и диск; сюда не входят публичный IP, резервные снимки, исходящий трафик сверх бесплатной квоты и резервное хранилище. Это только расчёт по текущим почасовым ставкам, не счёт и не оферта. Сервер, платные ресурсы и контейнеры не запускаются без отдельного согласия.

Минимальная схема — одна российская VM с зафиксированной версией Supabase Docker Compose, Caddy для HTTPS, закрытой панелью Studio и PostgreSQL. Это не отказоустойчивая архитектура: при сбое VM сервис остановится. Нужно настроить автозапуск, ежедневный шифрованный дамп PostgreSQL и копию Storage в отдельном российском хранилище, ограничить доступ к снимкам, хранить резервные копии по установленному сроку и регулярно проверять восстановление. При увеличении нагрузки или требованиях к доступности понадобятся отдельный узел резервирования и мониторинг.

Supabase self-hosting не предоставляет управляемые резервные копии, восстановление на момент времени и эксплуатацию сервера: за обновления, безопасность, резервирование и восстановление отвечает владелец. Полные требования по бэкапу и допустимому простою нужно согласовать до размещения.
